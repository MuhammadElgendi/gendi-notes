# Publishing a note

From "I have something to write down" to "it is live", end to end.

`deploy/README.md` covers building the **server** once. This covers the loop you
run every time after that. If the server is already up, you never need that
document again.

---

## The fastest way: the dashboard

With the site on GitHub Pages ([setup](deploy/GITHUB-PAGES.md)), open
`https://<you>.github.io/gendi-notes/admin/`, drop the `.md` file, pick the
section and folder, press **Publish to site**. It writes the frontmatter for
you, runs the same checks as the linter below before it lets you publish, then
shows the commit, lint, build and deploy until the note is live.

Everything below still applies — it is what the dashboard does for you, and the
way to publish from a terminal.

---

## The short version

```bash
# 1. create the file — filename MUST equal the slug in the frontmatter
cp templates/guide-template.md 08-observability/grafana/grafana.md

# 2. write it, then build: renders the site, regenerates INDEX.md, lints
node site/build.mjs

# 3. read it in a browser before calling it done
node site/serve.mjs                      # → http://localhost:8080

# 4. commit (INDEX.md is regenerated — include it)
git add -A && git commit -m "Add Grafana note"

# 5. push. The push IS the deploy.
git push github main          # GitHub Pages — pull --rebase first, see deploy/GITHUB-PAGES.md
git push production main      # the VM
```

A successful push prints the server's own output:

```text
remote: → linting
remote: Checked 22 notes — 0 error(s), 0 warning(s).
remote: → building
remote: → publishing to /var/www/gendi-notes
remote: ✓ deployed 23 pages
```

If you do not see `✓ deployed`, **nothing was published** — the previous version
is still live. Go to [If the deploy fails](#if-the-deploy-fails).

## 1. Put the file in the right place

Notes live only in the numbered domain directories. Anything outside them is
ignored by the build, which is why `deploy/` can hold a README without becoming
a note.

| Rule | Consequence if you get it wrong |
|:---|:---|
| **Filename without `.md` must equal `slug:`** | Build error, names the expected slug |
| One concept, one file, in the domain that owns it | Duplicated concepts diverge and one becomes wrong |
| Symptom-shaped notes go in `*/troubleshooting/` | At 3am you search the symptom, not the cause |

```bash
# the directory usually already exists — it is a .gitkeep placeholder
ls 08-observability/
```

Start from a template rather than a blank file. Both carry the `:::ar` and
`:::q` scaffolding, and a note without the Arabic layer is half a note here:

```bash
cp templates/guide-template.md      <domain>/<topic>/<slug>.md   # a tool or technology
cp templates/interview-template.md  13-interviews/<area>/<slug>.md
```

---

## 2. Fill the frontmatter first

The build **fails** without it. Seven keys are required:

```yaml
---
title: Grafana                       # human title, becomes the H1
slug: grafana                        # MUST equal the filename without .md
type: guide                          # guide | concept | troubleshooting | interview | cheat-sheet | ...
domain: 08-observability             # the top-level directory it sits in
tags: [grafana, dashboards]
keywords: [panel, datasource, promql,
           جرافانا, لوحات, مراقبة]   # English AND Arabic search terms
level: 2                             # 1-5
status: stable                       # seed | draft | stable
prerequisites: [prometheus]          # slugs — checked, must resolve
related: [prometheus]                # slugs — checked, must resolve
updated: 2026-09-11                  # YYYY-MM-DD
---
```

`keywords` feed the sidebar filter, so Arabic terms there are what let you find
a note by typing `مراقبة`. A wrapped `[...]` list is fine — the parser folds it.

---

## 3. Write it in the house style

The full rules are in [CONTRIBUTING.md](CONTRIBUTING.md); the parts the linter
cannot check for you:

- **Every section twice.** English carries the spine; `:::ar` re-explains the
  same idea from the beginning, in Egyptian Arabic, rather than translating it.
- **Technical terms stay English** inside the Arabic — `Pod`, `SIGTERM`.
- **An Interview corner** at the end: `:::q` cards with the model answer *and*
  what the interviewer is really testing.
- **Diagrams use `→ ← ↑ ↓` only.** The `▶ ▼ ◀ ▲` triangles fail the build —
  they are missing from Consolas, so every box drifts out of alignment.
- **Close every `:::`.** An unclosed one silently swallows the rest of the note;
  the build now catches it and prints the line number.

## 4. Build locally before you commit

```bash
node site/build.mjs            # build + regenerate INDEX.md + lint
node site/build.mjs --check    # lint only, no writes, exit 1 on error
```

:point_right: **Run the full build, not just `--check`, before committing.**
`--check` does not write, so `INDEX.md` is only regenerated by a full build. The
server regenerates it too, but inside `/srv/gendi-notes/src` where it is never
committed back — so if you skip this, the `INDEX.md` in git slowly goes stale
even though the live site is correct.

Run it **from inside the notes directory**. `node` resolves `site/build.mjs`
relative to the working directory, so running it from `~` gives
`Cannot find module '/home/you/site/build.mjs'`.

What the linter will stop you on:

| Error | Meaning |
|:---|:---|
| `frontmatter missing required key: X` | Add it |
| `slug "x" must match the filename "y"` | Rename the file, or fix `slug:` |
| `related references unknown slug "x"` | That note does not exist — create it or drop the reference |
| `wikilink to unknown slug: [[x]]` | Same, for a `[[x]]` in the body |
| `:::ar is never closed — it swallows the rest of the note` | Add the missing `:::` |
| `diagram uses "▼" — use "↓"` | Replace the glyph |
| `broken link: path.md` | The target file does not exist |

---

## 5. Preview it

```bash
node site/serve.mjs            # http://localhost:8080  (needs a build first)
node site/serve.mjs 3000       # different port
```

Problems of *rhythm* — a wall of text, three callouts in a row, an Arabic block
that reads like a translation — are only visible rendered. Check the note in
both themes and at a narrow width; the theme toggle is top-right.

---

## 6. Commit

```bash
git add -A
git commit -m "Add Grafana note"
git status --short              # should be empty
```

`site/dist/` is gitignored, so the built output never enters the repo. `INDEX.md`
**is** tracked — commit the regenerated version along with the note.

---

## 7. Push — the push is the deploy

```bash
git push production main
```

The [`post-receive` hook](deploy/post-receive) on the server then:

```text
1. checks out main into /srv/gendi-notes/src
2. runs `node site/build.mjs --check`   ← if this fails, it stops here
3. runs the build
4. rsync --delete  site/dist/  →  /var/www/gendi-notes/
```

Two things follow from that order:

- **A broken cross-link cannot reach the site.** The lint runs before the build,
  so a failed deploy leaves the previous version serving.
- **Only `main` deploys.** Pushing any other branch prints
  `→ ignoring refs/heads/x (only main deploys)` and does nothing.

`rsync --delete` means pages for notes you deleted are removed from the live
site, rather than lingering forever.

---

## 8. Verify it is live

```bash
curl -sI -u '<user>:<password>' https://gendi-notes.publicvm.com/ | head -1
```

Then open the note itself and check the sidebar lists it. The hook's
`✓ deployed N pages` count should be **notes + 1** (the home page).

## Deploying from the office network

The corporate web filter blocks `publicvm.com` — it is a free dynamic-DNS
domain, a commonly blocked category. DNS is intercepted and answers with the
filter appliance (`208.91.112.55`), so SSH dials the wrong host:

```text
ssh: connect to host gendi-notes.publicvm.com port 22: Network is unreachable
```

The server itself is fine. Push straight to its IP, keeping host-key
verification against the name you already trust:

```bash
GIT_SSH_COMMAND='ssh -4 -o HostName=130.61.40.218 -o HostKeyAlias=gendi-notes.publicvm.com' \
  git push production main
```

`HostKeyAlias` is the important half: it checks the server's key against the
`known_hosts` entry for the hostname, so this is not a trust-on-first-use
shortcut. The keys that must match:

| Type | Fingerprint |
|:---|:---|
| ED25519 | `SHA256:gcCBpWLwWuZe0n5P06/uzVnckXOqWljfOaRbCqm/wCY` |
| RSA | `SHA256:+QYI9H5MxD3sYr2skfc4tGZ0cahgxOAkToKI1AJqXNY` |

If ssh ever reports a **different** fingerprint for that IP, stop — that is the
one case where you should not push.

Check quickly whether you are on a filtered network:

```bash
getent hosts gendi-notes.publicvm.com
# 130.61.40.218  → fine, push normally
# 208.91.112.55  → filtered, use the command above
```

From home or a phone hotspot, plain `git push production main` works.

## If the deploy fails

| What you see | Cause | Fix |
|:---|:---|:---|
| `Checked N notes — 1 error(s)` then no `✓ deployed` | The lint caught something. **Nothing was published** | Fix it locally, commit, push again |
| `Network is unreachable` / `Connection timed out` | Corporate DNS interception | [Deploying from the office network](#deploying-from-the-office-network) |
| `Permission denied (publickey)` | Wrong key, or too many keys offered | `ssh -v`; add `IdentitiesOnly yes` + an explicit `IdentityFile` in `~/.ssh/config` |
| Push succeeds, hook silent | Pushed a branch other than `main` | `git push production main` |
| Push succeeds, site unchanged | Hook not executable | `chmod +x /srv/gendi-notes/repo.git/hooks/post-receive` |
| `node: command not found` in hook output | Non-interactive SSH has a minimal `PATH` | Add `export PATH=/usr/bin:/usr/local/bin:$PATH` near the top of the hook |
| `! [rejected] main -> main (fetch first)` | The server has a commit you do not | `git fetch production && git log production/main` — understand it before forcing anything |
| Live site 404s on the new note | It built, but the filename/slug is not what you linked to | Check the sidebar; compare `slug:` to the URL |

Server-side problems (certificates, Caddy, firewall) are in
[deploy/README.md](deploy/README.md#troubleshooting).

## Rolling back

The live site is whatever `main` points at, so rolling back is an ordinary
commit:

```bash
git revert <bad-commit>        # makes a NEW commit that undoes it
git push production main       # redeploys
```

Prefer `revert` over `reset --hard` + force-push: the server's checkout is
`checkout -f main`, so a rewritten history works, but you lose the record of
what happened and anyone else's clone diverges.

## Publishing without git (emergency only)

If you must get a file live while git is unavailable, build locally and copy the
output straight to the webroot:

```bash
node site/build.mjs
rsync -az --delete site/dist/ ubuntu@130.61.40.218:/var/www/gendi-notes/
```

:warning: **This is temporary and will be silently reverted.** The next
`git push` runs `rsync --delete` from the server's own checkout, which erases
anything not in the repository. Treat this as a way to unblock yourself for an
hour, then commit the change properly.

Never hand-edit files in `/var/www/gendi-notes/` — they are generated output,
and the next deploy overwrites them.

## Checklist

- [ ] Filename matches `slug:`
- [ ] All seven frontmatter keys present; `prerequisites` / `related` resolve
- [ ] Arabic keywords added so the sidebar filter finds it
- [ ] Every section has its `:::ar` counterpart, and it re-explains rather than translates
- [ ] Interview corner present, with *what is really being tested*
- [ ] Diagrams use `→ ← ↑ ↓` only
- [ ] `node site/build.mjs` — 0 errors, and `INDEX.md` regenerated
- [ ] Read it rendered, in both themes
- [ ] Committed, including `INDEX.md`
- [ ] Pushed, and saw `✓ deployed N pages`
- [ ] Opened the live URL and found it in the sidebar
